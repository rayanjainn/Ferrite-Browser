| T-214 | done (workaround identified; not a code fix) | process/infra | **Sharing `CARGO_TARGET_DIR` across git worktrees can serve a stale, deleted worktree's compiled test binary — a real, reproducible false-CI-failure source, not a code bug.** Root cause: `env!("CARGO_MANIFEST_DIR")` (used by `ferrite-core`'s and `ferrite-model`'s fixture-path resolution — see ADR-worthy fix history on `fixtures::fixture_dir()`) gets baked into a crate's compiled *incremental codegen units* at compile time. When a crate is compiled once from inside a git worktree (e.g. an isolated agent's `.claude/worktrees/agent-<id>/`) and the shared `~/.cache/ferrite-target` retains that build's incremental cache, `git worktree remove`-ing the worktree does **not** invalidate those cached codegen units — rustc's incremental system intermittently reuses them for a later, textually-identical compile from the *main* checkout, producing a test binary whose baked-in `CARGO_MANIFEST_DIR` points at a path that no longer exists. Not filed against any crate — this is a rustc/cargo incremental-compilation interaction with the worktree-per-agent workflow itself, not a defect in `ferrite-core`/`ferrite-model`'s source. Worth a `just` recipe (e.g. `worktree-done` wrapping `git worktree remove` + a target-dir clean) if this workflow continues to be used for future agent charters. |
